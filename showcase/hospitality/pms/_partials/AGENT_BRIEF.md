# Agent brief — building Azura Manager PMS screens

You are generating a slice of a 579-screen clickable HTML/CSS/JS prototype for "Azura Manager", the redesigned PMS for Azura Stays (a luxury villa rental/management company). This is presale/demo work the client intends to reuse as the basis for migrating their real legacy system — so build every screen for real, with real behavior, not a wireframe stub. Read every file below before writing anything; do not guess at the design system.

## Read these first, in this order

1. `output/prototype/ui-kit-brief.md` — the full design system decision record: color tokens, typography, spacing, the 12 sidebar groups (§5), archetype/tone, mock-data conventions, and the signature "Property Readiness" moment (§8, which you only reuse if your module is Properties — it's not repeated elsewhere).
2. `output/prototype/assets/css/global.css` — every CSS class you use already exists here (buttons, cards, stat cards, badges, tables, toolbar/chips, tabs, settings-nav, forms, switch, modal, empty-state, toast). Do not invent new component classes for things this file already covers; add screen-specific rules only in the screen's own `style.css`.
3. `output/prototype/assets/js/global.js` — shared helpers: `MM.openModal/closeModal`, `MM.showToast`, `MM.bindFormValidation/validateForm`, `MM.simulateSave`, `MM.uid`, sidebar collapse/accordion/tooltip/flyout behavior (already wired, you don't touch it), and the shared mock casts `MM.MOCK_PROPERTIES`, `MM.MOCK_OWNERS`, `MM.MOCK_GUESTS`, `MM.MOCK_STAFF`, `MM.MOCK_BOOKINGS`, `MM.MOCK_VENDORS` — reuse these entities by name/id wherever your module's screens reference a property/owner/guest/staff/booking, instead of inventing new ones, so the same "Villa Sapphire Cliff" or "James Whitfield" appears consistently across modules. You may add new arrays for entities the shared file doesn't cover (e.g. maintenance tickets, garden/pool tasks) — put those in your screen's own `script.js`, keyed so other screens in your module can reuse them too if relevant.
4. `output/prototype/_partials/shell-module.html` + `output/prototype/_partials/README.md` — the exact sidebar/topbar markup you paste into every screen, and the 2-3 things you're allowed to change per screen (active item, open group, and — only for Owner Portal/Guest Portal screens — the logged-in persona). 5. `output/prototype/screens/dashboard/index.html` and `output/prototype/screens/auth/log-001-login/index.html` — the two already-built, QA'd anchor screens. The skill reference docs at `/Users/thinhnd1/.claude/plugins/cache/presale-skills/hbg/0.5.0/skills/building-prototype/reference/`: `screen-generation-guide.md` (per-screen-type rules: list/CRUD screens, forms, settings screens, module landing pages), `interactivity-guide.md` (you follow the "main workflow — full interactivity" rules for **every** screen, not just secondary ones — see below), `form-containers.md` (how to choose modal vs slide-over vs dedicated page for a given form), `craft-and-qa.md` (the anti-AI-slop checklist — no emoji icons, no fake status dots, no decorative gradients on data screens, etc.), and `specialized-screens.md` if any of your screens are a calendar/Kanban/wizard/file-manager/approval-queue type.

## Non-negotiable rules

- **Every screen gets full interactivity**, per `interactivity-guide.md`'s "main workflow" column — real client-side validation (required/email/phone/number, checked on blur AND submit), a simulated save delay (`MM.simulateSave`), `localStorage` persistence keyed by your module name (e.g. `localStorage['mm_maintenance_tickets']`), real filter/search/sort over the merged mock+localStorage dataset, and a confirm-before-delete modal. This is an explicit client instruction (they're reusing this prototype for a real migration) — do not build any screen as click-only static UI, even ones outside the 4 headline workflows (Booking, Property/Owner, Field Ops, Guest Portal).
- **Full pages only get their own folder.** Sitemap rows marked `Popup` in the `Type` column are NOT separate folders — embed them as `.modal-overlay` markup (see the Login screen's Forgot Password modal, or CMS's original popup pattern) directly inside the HTML/script.js of the parent screen named in their "Opened From" column. A screen's folder is `screens/<module-slug>/<code-lowercase>-<slug>/index.html` + `style.css` + `script.js`, where `<module-slug>` is your module's folder slug from `ui-kit-brief.md` §5's mapping table, and `<code-lowercase>-<slug>` is e.g. `prop-035-view-property-details`.
- **Reuse the sitemap's real navigation.** Wire breadcrumbs and in-page links using the actual "Opened From"/"Navigates To" columns for your codes — don't invent new cross-links, and don't link to a screen outside your batch that doesn't exist yet if you're unsure of its folder slug (in that case, still write the correct href per the naming convention above so it resolves once that other agent's batch lands — do not skip the link or point it at `#`).
- **Only screens with a sidebar entry get an `active` class.** Per `ui-kit-brief.md` §5, most of your screens (edit/view-detail/report/popup-parent screens) are NOT in the sidebar at all — for those, leave every nav item un-active but still open the correct parent group, and make sure the breadcrumb correctly names the module.
- **Legacy spec ≠ visual target.** Some `en-screens/*.md` files describe a very thin legacy screen (e.g. one dropdown and two AJAX widgets). Your job is the *redesigned* version: apply the full design system (KPI/stat cards where relevant, proper empty states, icons, toolbar) even when the legacy screen was sparse — never ship a screen that looks like the raw legacy description turned into HTML with no design applied.
- **Mock data:** 5-10 rows per list screen, English/Western names, real status diversity (not all-green), reusing the shared mock casts where the entity overlaps another module (bookings, properties, owners, guests, staff), documented in `global.js`.
- **No emoji icons, no fake decorative status dots, no Lorem ipsum, no "Trusted by hundreds of businesses" filler copy** — see `craft-and-qa.md`'s ban list.
- After finishing each full-page screen, append one line to **your own progress file** `output/prototype/progress-<your-batch-name>.md` (create it if it doesn't exist): `- [x] <module-slug>/<code-lowercase>-<slug>`. Do **not** write to the shared `output/prototype/progress.md` directly — many agents run in parallel and concurrent writes to one file will corrupt it; your batch-specific file gets merged in afterward.
- If a screen type doesn't fit any pattern you have guidance for (e.g. a Kanban board, calendar, map, wizard), check `specialized-screens.md` before improvising.

## When you're done

List the folders you created, note any screen you deliberately deferred/simplified and why, and flag anything in the sitemap that seemed ambiguous (e.g. a screen whose "Navigates To" target doesn't clearly map to one of the sidebar modules).
